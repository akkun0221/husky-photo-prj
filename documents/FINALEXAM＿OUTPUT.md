# 1. SSR / SSG / CSR / ISRの使い分け

a. 公式ドキュメントの Rendering のセクションを読んで、CSR / SSR / SSG / ISR
それぞれが「いつHTMLを生成するか」という軸で違いを理解してください。
b. 手を動かしてそれぞれの違いを確認してください。

- Next.js の App Router を使って、Server Component / Client Component の使い分けを
  実際に試してみてください。ページごとに dynamic / static のレンダリング挙動の違いを確認してみてください。
- 余力があれば、Vite で SPA, SSR, SSG を作ってみてください。
  各レンダリング手法についての理解がより深まると思います。
  c. 「XXという特徴のあるシステムの場合はSSR / SSG / CSR / ISRのどれが最適か」を
  言語化できるようにしてください。

---

## 回答：

a. CSR / SSR / SSG / ISRそれぞれHTMLを生成するタイミングの違いを以下に示す。

- SSR: Server Side Rendering.
  - サーバ側でリクエストの度にHTMLを生成する。
  - 常に最新ページを見ることができる反面、JSでの動きが多いサイトなどは初期描画に時間がかかる。
  - ただし、常に最新情報を表示されていないといけないECサイトやSNSなどではよく使われる。
- SSG: Static Site Generation. ビルド時にHTMLを生成する。
  - デプロイしたタイミングでHTMLが生成される。
  - その後のリクエストは基本的に最初に生成されたHTMLが配信される。
  - 表示速度は非常に速い反面、情報の更新がされないので情報を更新したい場合は再ビルドを行ったり、強制的に再生成をする処理をかませる必要がある。
  - 頻繁な更新のないブログサイトやコーポレートサイトのIR情報以外などで使用されるケースが多い。
- ISR: Incremental Static Regeneration. ビルド時にHTMLを生成するが、一定時間ごとに再生成する。
  - 基本的にはSSGと同じくビルド時にHTMLは生成される。
  - 違いは、ISRの方は一定期間を設けることができる（1時間おき等）ので、その期間を過ぎた後にリクエストがあるとそこで再度取得を行いHTMLを生成する。
  - 頻繁な更新がないサイトや何かしらの監視ログなどを表示する場合に利用されるケースが多い。
- CSR: Client Side Rendering.
  - クライアント側でHTMLを生成する。
  - 上記、3つはサーバーサイドでHTMLが生成されるがCSRのみクライアントサイドで生成される。
  - サーバーからは中身が空のHTMLが送られてきており、ブラウザ側でJSを読み込みリクエストがあるとそこでHTMLを生成する。
  - 初期描画は遅いが、その後の処理はリクエスト頻度を抑えられるため速い。
  - SPAのサイトでは1つのURLで様々なページを見ることができるためCSRが利用される。
  - 恐らくポケモンカードの一覧紹介ページはSPAでCSRが採用されている。

b. 手を動かしてそれぞれの違いを確認してください。

実際の今回のサイトでいうと、

- / :ここは、訪問者が最初に訪れるページであり、最新情報でないといけない。
  ただし、更新タイミングは管理者である俺が新しいライブに写真をアップロードしたタイミングなので、
  描画スピードと最新情報のバランスによりSSGを採用し、写真をアップロードしたタイミングで強制的に再ビルドをおこなっている。
  SSGのメリットである表示スピードに振っており、更新タイミング（最新化）は俺の写真アップロードのみなのでこちら起因でレンダリングする以外にないためSSGにしている。
  revalidate=("/")のようにして写真アップロード後に再ビルドを行っている。
- /lives : こちらもトップページと同じ理由でSSGを採用している。
  更新タイミングについては、ライブ終了後に写真のアップロードを行うので、トップページと同様の理由でSSGを採用している。
- /lives/[id] : 基本的にはトップやライブ一覧と同じ考えなので、SSGを採用しているが、写真の枚数が多い場合を考慮して
  無限スクロール（ユーザー体験を優先しているため、実際は仮想スクロール）を採用している。
  そのため、初期描画時は初めにビルドされたときの写真しか表示されていないがスクロールをすることによりCSRでレンダリングが走り写真は順次全て表示される仕組みになっている。
- /members : SSGを採用しており、理由はトップやライブ一覧と同様なので割愛。
- /admin系 : 管理サイト側は、常に最新でないといけない（同じ日に同じ写真を追加しないよう）ためSSRを基本的に採用している。
  削除処理等も行うため、常に最新情報を取得しつつ表示スピードも考慮して初期描画数などに制限を設けている。

c. 「XXという特徴のあるシステムの場合はSSR / SSG / CSR / ISRのどれが最適か」を言語化できるようにしてください。

一概には言えないが、例として
CSR : SEO対策が一切不要なサイトであれば、初期が空→アクセス時に最新情報で問題ない。あとは管理画面のダッシュボードなど。
その他、マイページなどのログインを伴うページもSEO対策が不要かつ最新情報はほしい、ユーザビリティは高い方が良いので良い。
SSR : リアルタイムで情報が更新され、SEO対策が必須のサイトはほぼSSRが採用される。
その上で、人によって表示されるデータが異なるためタッチの差で売り切れになるなどの問題は起きるが仕方のない部分。
SSG : コーポレートサイトや個人ブログなど基本的に更新がかからないサイト。
あとは、新商品のティザーサイトなどはアクセスが急増するが常に更新がかかるわけではないのでSSGを採用し爆速で表示させる必要性があったりする。
ISR : 大量のページがあり、かつ部分的に最新情報が必要な場合に採用するケースが多い。
例えば、ECサイトの商品詳細ページなど。

# 2. コンポーネント設計

a. アトミックデザイン（Atoms / Molecules / Organisms / Templates / Pages）の考え方を理解してください。
各レイヤーの責務の違いと「どこに何を置くか」の判断軸を整理しておくと、チームへの設計説明がしやすくなります。

b. Feature-Sliced Design や Bulletproof React を一読し、ディレクトリ構成の設計パターンを把握してください。

c. 「このコンポーネントはどのレイヤーに置くべきか」「このロジックはカスタムフックに切り出すべきか」などをチームに説明できるようにしてください。

---

## 回答：

a. それぞれの考え方について

- Atoms : ボタンや入力フォームなどこれ以上に分解のできない最小のUIパーツ
- Molecules : Atomsを組み合わせたもの。例えば、ラベルと入力フォームとボタンで検索フォーム。
- Organisms : Atoms,Moleculesを組み合わせたもの。例えば、ヘッダーやフッターなど。このレベルになると他プロジェクトへの再利用は難しいが同プロジェクト内であれば可能。
- Templates : Organismsを組み合わせたもの。例えば、サイトのレイアウト。どこに何を表示するかの骨組み。実際のデータは入らない。
- Pages : Templatesにデータを流し込んだもの。実際のページとして表示される。

### よくある落とし穴

- ModulesとOrganismsの境界線があいまいになりがち。
  →他コンポーネントに依存しない状態の再利用可能なコンポーネントはModules、複数のAtomsやModulesが組み合わさり意味が付いているものはOrganismsとすると良い。
- コンポーネント数がえぐい数になりがち。
  →厳密にするほどファイル数が増えてしまい管理が煩雑になってしまう。昨今ではアトミックデザインを踏襲しつつも3階層で作られることも多い（ex. components / layouts / pages）。

b. FSDとBRについて

- FSD : 依存関係を下から上へという一方向に強制をすることで依存の循環を防ぐ。開発人数の多いプロジェクトにおいて、コードの属人化を防ぐのに適している。
- BR : 機能ごとに自己完結させることで関心の分離を行い他に影響を与えずらい。導入コストが低く、小〜中規模ならBRで十分なケースが多い。

今回のプロジェクトでは、FSDを採用したのでそれについて詳細に記載する。
以下、上位レイヤーから下位レイヤーの方向で説明。

- app : アプリ全体の初期化やグローバルCSS、ルーティングの定義などを行う。
- pages : 実際の画面。Next.jsのApp Routerの場合、appディレクトリがこれを兼ねている。
- widgets : 複数のコンポーネントを組み合わせたもの。例えば、ヘッダーやフッターなど。このレベルになると他プロジェクトへの再利用は難しいが同プロジェクト内であれば可能。(TemplatesとOrganismsの中間に位置するイメージ)
- features : このプロジェクト特有の機能のまとまり。これ単体では1機能とはならないが、プロジェクト内で再利用できる単位。（Organisms相当）
- entities : データ構造やAPIなどバックエンドとの連携やビジネスロジックの層。
- shared : 特定のビジネスロジックに依存しないアプリ全体で再利用する汎用的な部品や共通ロジック（Atoms/Molecules相当）

## よくある落とし穴

- features VS widgets
  レイアウトに関わるかどうかで切り分けると良い。
  pagesにfeaturesで配置しても結果としても同じ表示になるが、のちのレイアウト変更等を考えたときにpagesを直接編集することになる。
  これをwidgetsにまとめておくことでそちらの修正をするだけで他にも使いまわすことができる。

c. 説明時の切り分けについて

### コンポーネントのレイヤー説明をするときの切り分け3段階

これらをまとめておくと説明要求があった際に伝わりやすくなるはず。

[質問1] 独自のビジネス知識やデータ構造（User, Product 等）を持っていますか？
├─ NO ──> 【Shared】（例: 汎用Button, Modal, 共通Utils）
└─ YES ─> [質問2] へ

[質問2] 状態変化（API通信、クリック時の挙動、バリデーション等）を持っていますか？
├─ NO ──> 【Entities】（例: ProductCard ※データを渡して表示するだけ）
└─ YES ─> [質問3] へ

[質問3] それは「1つの具体的な行動（機能）」ですか？ それとも「画面の領域（レイアウト）」ですか？
├─ 行動 ─> 【Features】（例: AddToCartButton, FollowButton）
└─ 領域 ─> 【Widgets】（例: ProductActionPanel, Header）

### カスタムフック化するかどうかの切り分け3基準

基準1：複数のコンポーネントで「同じロジック」を共有したい（再利用）
内容: 画面の見た目は違うが、裏側のデータ制御や状態管理が全く同じ場合。

例: useAuth（ログイン状態の管理）、useWindowSize（画面幅の検知）

基準2：コンポーネントのコード長を減らし、「見通し」を良くしたい（関心の分離）
内容: たとえ1つのコンポーネントでしか使わないロジックであっても、useEffect や複数の useState、API通信のハンドリングが肥大化して、UI（JSX）のコードが埋もれてしまう場合。

効果: コンポーネント側は「何を画面に表示するか（UI）」に集中し、フック側は「どうデータを処理するか（ロジック）」に集中できます（UIとロジックの分離）。

基準3：ロジック単体で「ユニットテスト」を書きたい（テスト容易性）
内容: 複雑な条件分岐やデータ加工が伴うロジックで、UIのレンダリングを挟まずに、関数（ロジック）単体としてテストを網羅したい場合。

効果: renderHook を使って、ロジックのバグを高速に検知できるようになります。

# 3. Provider 設計

a. React の Context API が何を解決するものかを理解してください。
b. 小さいアプリで認証・テーマ・ロケールなど責務の異なる Provider を実際に作り、ネストの整理を体験してください。
c. 「何を Provider で管理し、何を管理しないか」の方針を言語化できるようにしてください。Provider が深くネストしてしまうパターン（認証・テーマ・ロケール・トースト通知などを全部 Context で管理してしまうケース）と、Zustand など状態管理ライブラリへの切り出しで回避する方法を説明できる状態を目指してください。

---

回答：

a. Context API が解決するもの

Propsのバケツリレーを回避するための仕組み。
グローバル関数・変数のようなものでプロジェクト全体で管理をされているものになる。
そのため、テーマ切り替えやセッション情報、多言語化対応において効果を発揮する。
逆に、高頻度で更新されるようなものをContextの中に入れてしまうと、都度すべてのコンポーネントが再レンダリングされてしまいパフォーマンスが落ちてしまうので注意が必要。

b. 今回のキャッチアップ用プロジェクトの中で体験は出来ている

各ページで更新頻度や用途の異なるProviderが複数あり、レンダリング手法と共にProviderをどのように設計するかを体験できた。
主な学びは、レンダリング手法を主とした考え方だが更新頻度を主軸にレンダリング手法とProviderの粒度を決めていった。

c. Provider VS Zustandの使い分け

Providerには、更新頻度が低いアプリ全体や特定の広い領域（管理画面全体みたいな）の環境変数的な立ち位置にあるものを使用する。
逆に写真のあるライブ一覧の表示やどのメンバーが表示されているのかというような今回のプロジェクトでは比較的参照・更新頻度の高いものはZustandで管理する方が適している。
理由としては、Provider（Context）で管理されているものはどれかいずれかの変更が入ると全てを再レンダリングしてしまうのでパフォーマンスに影響を出してしまう。

## 悲劇1

Propsのバケツリレーを回避するために導入したはずが、今度はコンポーネントのバケツリレーやヘビーウェイト化になってしまい本末転倒。

## 悲劇2

様々なグラフを管理しているダッシュボード画面でトースト表示をしただけなのに、全てのグラフコンポーネントが更新されてしまい処理が重くなる。

たとえ話で言うと、特進クラス～ヤンキークラスまで管理している先生が複数いたとき、
ヤンキークラスでタバコが見つかったら、特進クラスまで含めて全て持ち物検査を行う学年主任がContext
かたやZustandはトイレに設置してある火災報知器。トイレで火災報知器がなったら、その時出入りをしていた生徒だけに持ち物検査を行う体育教師。
補足として、useStateだけどこれはそれぞれが授業中に取ってるノートのようなもの。勉強をないがしろにしてるヤンキーは授業ごとに捨てるし、特進クラスの子は卒業までは保管してたり、各々の管理によるもの。

# 4. 状態管理ライブラリの選定

a. Zustand・TanStack Query・Jotai・Redux それぞれが「何の状態を管理するか」という軸で違いを理解してください。
b. 手を動かしてそれぞれの役割の違いを確認し、「どんなPJではどのライブラリが最適か」を言語化できるようにしてください。

---

回答：

a. それぞれの管理するもの
Zustand: クライアントで完結するグローバルな状態管理。対比はキャッシュ。
TanStack Query: サーバーキャッシュ管理。DBやAPI通信で引っ張ってきたデータを管理するもの。
Jotai:　Atomと呼ばれる小さい単位で状態管理を行う。画面内の要素が複雑に依存しあっているUIにおいて効果を発揮。Web上で動くデザインツールなどはこれに当たる。
Redux: 上3つの全てを一元管理するもの。一時期のデファクトスタンダードだったが現在はウェイトヘビーなため選択肢としては避けられることが多い。

b. 向いている・向いていないプロジェクト

Zustand + TanStack Query: ほとんどのプロジェクトで活用できる組み合わせ。DBがあり、それなりにリッチな画面がありという現在のモダンな画面においては最強の組み合わせ。
Jotai: Zustandを導入することによってむしろPropsバケツリレーが発生するような特殊ケース。例えば、デザインツールやノーコードツール、ドラッグ＆ドロップを多用するような画面など。
Redux: 大規模開発において、厳密にルールが定まっている場合や、既にReduxでの運用を正としているようなプロジェクトを引き継ぐ場合。新規の選択肢ではあまり出てこない。

# 5. デプロイ戦略

a. Vercel・Cloudflare Workers それぞれの仕組みと特徴を理解してください。
b. 手を動かしてデプロイを体験してください。

- Vercel は Git 連携による自動デプロイを試し、PR ごとにプレビュー環境が作られる流れを確認してください。CLI や GitHub Actions 経由でのデプロイも一通り触れてみてください。
- Cloudflare Workers はGitHub Actions 連携でデプロイしてみてください。Edge Runtime 前提のため Node.js 固有 API（fs など）が使えない制約を実際に確認しておくと良いです。
- Vercel の Middleware（middleware.ts）を使った Basic 認証をステージング環境にだけかける構成を試してみてください。
- 「このPJでは Vercel と Cloudflare Workers どちらが適切か」をコスト・制約・要件の観点から説明できるようにしてください。

---

回答：

a. VercelとCloudflareの違いについて

一番の違いは、Node.jsで動くか、Edge Runtimeで動くかという点。
これにより、Vercelの方では、Next.jsの機能を全て活用できる一方でアクセスがない状態が続いた際のコールドスタート問題や商用利用しようと思った際の従量課金制の金額の跳ね上がり方が顕著。
逆にCloudflareはEdge RuntimeのためNext.jsの一部の機能は使えないものの実装でどうとでもなる部分ではある。
また、ブラウザ側で動くためコールドスタート問題もなく、他機能と組み合わせれば一番不得意とされているISRも再現することは可能である。
元々の利用が商用利用を許可しているためサービスの規模によって拡張していっても従量課金制のコストも安く抑えられるケースが多い。
対比はAWSだが、どこまで拡張させるのかや知名度などが主戦場となる。

b. Vercelを使用してデプロイ体験を実施
